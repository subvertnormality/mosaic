These two delivery plans were split at the user's request after Paranoia Claude Fable's round-3 review of the combined revision returned NOT-BLOCKED (zero blocking debt, all eight tracked classes closed, two active external claims supported). Round 3's sole minor wording finding is corrected in the nudge plan by giving the requested range one authoritative definition. The split documents themselves have not had a further Fable review. ## 1. Outcome, scope and dependency boundary

Deliver working global MIDI parameter-lock lookahead, independently of step nudge. Notes stay in their existing producing pulses; swing/shuffle, step order and note decision timing retain their current behaviour. Lead is specified in physical milliseconds. Lead 0 retains the existing fast path and byte/timeline behaviour. Exact nonzero lead is an experiment until the explicit hardware acceptance below passes.

This delivery contains pure step/parameter preview, immutable occurrence IDs, pattern epochs, a bounded cancellable value queue, value commit/resend tracking, capture/oracle improvements and timing feedback. Reuse existing base-onset projections after extracting and testing their pure recurrence; do not add shifted onset dispatch, per-onset offsets, coincident-step waves, nudge persistence, a Nudge row, or nudge-specific projection consumers. There is no future-nudge dependency in its release gate.

The follow-on document is [Step nudge — later delivery](step-nudge-plan.md). Its only architectural prerequisites are stable occurrence identity, pure base-onset projection, pattern fences, parameter preview, generation cancellation and the independently testable intended-time oracle. Do not implement unused offset APIs speculatively.

Keep global lead only and immediate start only. Residual R-PER-RECEIVER belongs to a future device-configuration workstream: completion requires persisted route/channel override keys, shared-receiver policy, two unequal leads on one port in emulator and hardware, bounded timer count and UI/docs/images. Residual R-PREROLL belongs to a future transport workstream: completion requires count-in clock/Start/Continue/SPP semantics, external-slave restriction, live-input policy and startup emulator/hardware coverage. Neither feature is advertised or required by this delivery.

No first-note-only delay: it shortens the next interval and can reverse ordering. No constant added latency. No pulse-counted note delay. Preserve exact-deadline/no-slack behaviour for any remaining deadline queue; a pulse rescues only overdue output.

## 3. Independent intended-time oracle and acceptance numbers

Build fixture-side intended timelines from public input schedule, fixture values and explicitly specified arithmetic. Do not call the production projection/resolver as the expected-value oracle. Anchor to Play/Start/input MIDI-clock capture, not notes[0]. Preserve the original relative-origin statistics alongside new absolute anchoring for baseline comparison; do not replace historical results. Correlate device/capture clocks using shared captured input markers, report maximum calibration residual. For external clock use captured input pulses for musical expectations; do not infer a perfect uniform tempo.

Each event has fixture occurrence identity, destination, type, bytes/value, expected pulse/time and tie order. Use distinct bounded fixture values/notes plus per-channel occurrence order to associate raw MIDI; reject ambiguity, missing or extra events rather than zip/min-truncating arrays. Same-value resend-off cases verify the previously committed value in force and must not demand a nonexistent new value. Expected suppression and conflict winners come from fixture policy, never from inspecting candidate output.

For actual a_i and intended t_i: placement error = a_i-t_i; interval jitter = abs((a_next-a_i)-(t_next-t_i)). Check per channel and per intended simultaneous group. Straight fixtures must reproduce old interval/service results exactly. Keep startup phase and clock/transport phase checks; no arbitrary first-note alignment can absorb a uniform shift. Constant initial offset calibration is fixed by input markers, never fitted to candidate notes.

Retain current hardware limits: event p99 <=10 ms with the existing one-stalled-step treatment; event max <=50 ms; final phase <=20 ms; step-jitter p95 <=5 ms and max <=10 ms; service p99/nominal step <=0.5 and maximum <=1.0. Preserve the original four unnudged fixtures, their service grouping and normalization. Include CPU, writes, bytes and pulse-duration distributions as diagnostics. Do not widen the existing gates.

NEW mandatory hardware lock metric: for locks-16 at both 25 and 50 ms (and added shared-route/gap/startup/NRPN fixtures), pair each audible note with its own winning value. Define observed lead G = captured note timestamp minus final serialized value-message timestamp. In this repository nrpn() serializes CC99,98,6,38 (lib/devices/midi_wire_output.lua:42-57); using the final emitted CC38 timestamp is the oracle's conservative local convention, not a claim about when every synth updates. Preserve all serialized byte-order assertions. Use the last relevant value for 7/14-bit CC as appropriate.

Expected gap E comes from the documented scheduling rule in section 5, including explicitly classified clamps. Report signed G-E, absolute error p95/max, and early/late counts. Controlled-time absolute gap error must be <=50 microseconds. Exact-ms hardware absolute gap error must be <=50 microseconds plus calibrated pairwise capture uncertainty U, for EVERY pair (thus p95 too). U must be independently bounded before trials and <=50 microseconds; otherwise the rig cannot qualify exact-ms timing and the result is inconclusive, not green. No pulse allowance, origin adjustment, or exclusion based on observed lateness. Gap-limited/startup values get their own exact E rather than being silently excluded. Receiver audio settling is outside this metric: MIDI capture proves delivery timing only, not acoustic response.

Use synthetic captures to prove these metrics fail on uniform hidden delay, ceil-to-pulse lead, wrong-value association, missing/extra messages, widened-gap classification, phase drift and staggered notes wrongly treated as one service group. Real-time emulator keeps its explicitly identified existing host tolerance; it does not certify hardware exactness. The semantic expected schedule is shared across controlled, real-time and hardware lanes; their measurement uncertainty is reported separately.

For the lead go/no-go: ten paired/interleaved windows of 80 intended step occurrences for EVERY workload/lead cell; every window must pass every applicable gate. No averaging away a failed window; retain startup and all ten windows. Runs are invalid only for predeclared capture loss, calibration failure or source/config identity mismatch; retain invalid runs and reason and rerun the entire cell. Timing failures are valid failures. Before campaign, freeze fixtures, reference commit, seeds, order and metrics in a manifest.

Lead-0 non-regression: baseline and candidate must each pass all windows, and candidate per-window p95 jitter and p99 event error distributions must have median paired change <=0 and empirical p95 paired change <=0, after fixed capture calibration. This deliberately conservative evidence rule may fail to establish non-regression amid noise; that means no acceptance claim, not a tolerance increase. Independently require exact lead-0 controlled-time byte/timeline parity. Summarize all window distributions and retain raw data.

## 4. Pure preview, occurrence identity and pattern boundaries

Read dirty recording locks as a distinct preview input; invalidate on record edits and retain current Off/slide behavior.

A bundle carries pattern epoch, track, occurrence, slot/address, physical connection, planned pulse/time, generation and value trajectory identity. Bound active horizon to the time needed for lead, capped at 64 future occurrences per channel; if the required horizon cannot be filled under that cap, mark horizon-limit and shorten effective lead, never silently overrun. Heap ordered by absolute deadlines/ordinal with one earliest-deadline wakeup; cancellation is by generation, with periodic bounded compaction. Do not create a timer per bundle, track or lead. Record maximum live/stale queue counts; cap at the maximum 16*64*10 parameter bundles plus bounded trajectory segments; reject/mark unsupported configuration rather than silently dropping active data. Slides store compact pure trajectory segments, generating due samples with bounded cursors instead of expanding every future sample in memory.

## 5. Lock scheduling, shared addresses and edits

An eligible step value is previewed regardless of eventual probability/condition success, as present process_params runs before step.handle. Define a PROTECTED ANCHOR as a planned eligible trig onset on a receiver channel, whether or not its eventual note decision passes. This conservative policy avoids predicting RNG. Include actual strum/arp/live note onsets when known; never promise advance for unannounced live notes. For each value event let T be its intended step/sample time on the existing base timeline, L requested lead, A latest protected anchor STRICTLY BEFORE T on that physical receiver channel. Desired send S=max(T-L,(A+T)/2) if A exists, otherwise T-L. Then clamp S to epoch start and preview-availability time. Effective lead E=T-S, with 0 lower bound; a deadline already missed is emitted promptly and recorded as late, not redefined into a successful E after observing output. Existing same-time trigless/slide events use this rule with their own T. Assigned step values use step T; each slide sample uses its scheduled trajectory sample T. No special lookahead note decision is made.

The planned conservative anchor rule is an explicit contract refinement: a skipped trig can limit lead. Where later decisions add notes that were not protected, do not retrospectively move sent values; mark interference and test the interaction. Fixtures proving exact lead exclude unpredictable live input by construction, never by observed failures. A deterministic live-note test asserts immediate thru and correct interference feedback, not impossible settling guarantees.

For simultaneous bundles on the SAME physical port/channel/address/T: explicit lock or active slide beats assigned fallback; among equal classes later existing sprocket order wins, then later slot order. Resolve before sending; emit only the winner and mark losers conflict. This is a new explicit cross-track rule, not an assertion that claim_stamp already arbitrates tracks. On a channel with distinct earlier T, use chronological committed bundles; do not let a later lookahead value overtake an earlier protected anchor. Keep NRPN four-message bundle contiguous with respect to competing NRPN bundles on that receiver. At coincident conflicting lock/note targets only the winner's value is promised; loser is visibly conflict-limited. At lead=0 keep the existing path byte-for-byte, including current duplicate-address precedence; new arbitration is enabled only for lookahead. Test both contracts explicitly.

Generation invalidation: lock/assigned/slide/record edits, routing/disconnect, ranges, mute, pattern edits, lead, applied feel/division changes, explicit internal tempo changes, Stop, panic and project load. Setting edits queued until a pattern boundary do not apply early. Updates before send replace unsent bundles. On send commit resend cache and occurrence ledger; cancelled previews never alter cache. Dirty already-sent values receive a corrective value at max(now, required midpoint), unless T already passed, in which case use the next eligible occurrence. Report shortened settling. Stop discards unsent speculative locks and onsets and releases held voices once; cleanup leaves no timers/held notes.

External MIDI clock: musical target pulses follow actual input-driven lattice pulses. Estimate remaining wall time from current clock estimate for pending absolute lock deadlines; update the ONE next wakeup on each input clock, no generation cancellation/re-emission merely because derived tempo changed. Once a bundle is sent it is never replayed for tempo drift. A stopped/missing clock cannot cause queued notes to fire; on clock loss cancel speculative lock wakeups until a valid resumed timeline, with clock-change feedback. Fixed-tempo external fixtures qualify exact-ms mode; injected abrupt external changes assert actual intended pulse consistency and honest reduced lead/late counters. Exact physical lead across unknowable future input changes is not promised. Generation changes still apply for actual transport/tempo-source changes.

## 6. Product contract, UI, persistence and migration

Successful lookahead mode retains midi_lock_lead_time (0..50 ms, same Parameter locks menu path and persisted project key). Default remains 25 only if exact-ms qualification passes. Global 0 selects old timing and bypasses preview cost. Notes, note-offs and clock/Start/Continue/Stop/SPP receive no added lock latency under the new nonzero contract. Live MIDI-thru always has zero added lock latency, including note-off; latch that policy for voices so a setting change cannot strand releases. Parameter advance affects MIDI only; n.b./audio/Crow parameter timing remains unchanged.

Immediate start for master and slave: send actual first-step locks before its note at the existing start onset; report effective lead zero when due together. Stored assigned values sent on Play are not substituted for those locks. The same epoch fence applies after global pattern resets. No first-note-only delay and no preroll UI/saved override is introduced.

Read-only timing feedback is in scope: add Channel Editor Timing page to existing page navigation, showing requested global lead, last effective scheduled lead for the selected channel, last measured dispatch lateness and sticky reason flags startup/pattern-boundary/spacing/late-edit/clock-change/conflict/horizon-limit. E2 chooses channel, E3 no-op, K2 clears diagnostic flags only. These are volatile fields, no saved parameter IDs; scheduler dispatch lateness is not a receiver measurement. Update through existing redraw invalidation, never draw in pulse callbacks. Test public-input navigation, values, clearing, save/load non-persistence and actual emulator images.

If exact-ms lead fails section 3, do not silently round and ship. Record failure and make a separate explicit pulse-advance experiment: S is latest legal pulse at or before T-L but not before the midpoint/epoch boundary; if that interval contains no pulse use the first pulse at/after the boundary up to T and report effective lead. This is a different contract, requires its own versioned matrix and same hardware repeats/note gates with pulse-intended expectations, NOT relaxed exact-ms tolerances. It is NOT enabled in this delivery unless that separate contract is reviewed and accepted. Otherwise release global lead disabled: runtime/default 0, existing saved nonzero request retained as legacy metadata for possible future migration, visible Lead unavailable on CM3+; no automatic re-enable and no queued delayed notes. Test loading old projects/new projects, public parameter changes and persistence. README/cheat sheet explicitly state availability. Do not label unsupported 25 ms as default working timing.
