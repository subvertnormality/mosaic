# Norns UI alignment: feasibility and scope

Date: 3 October 2026. Status: design assessment, not an implemented UI change.

## Recommendation

Use a stable vertical list for choosing destinations, selecting editable fields and assigning parameters throughout Mosaic. Keep the actual musical visualizations: pattern cells, playback indicators, output dashboards and any diagram whose position conveys musical information. A consistent navigation system does not require turning the whole instrument into a text menu.

The playful animations can stay. Their position and purpose should change: animate an icon or a musical visualization beside stable information, rather than moving the labels and values the player is trying to read. This is feasible without rewriting the sequencer or replacing norns' own parameter menu.

The change is significant enough to require new application-level acceptance tests and newly captured manual examples. It is not only a cosmetic CSS or renderer adjustment.

## What the code actually does today

The live path is `lib/ui.lua` → `lib/ui_live.lua` → `lib/ui_router.lua` and `lib/ui_render.lua`. The old page objects under `lib/pages/` still own values, drafts and musical edits; the live layer wraps those owners through `lib/ui_adapters/`. Therefore, converting only legacy `vertical_scroll_selector.lua` or the old page drawing callbacks would not realign the UI the player actually sees.

`docs/ui-reimplementation/spec.json` is the declarative source for the runtime registry. `lib/ui_spec_data.lua` is generated by `docs/ui-reimplementation/tools/export_runtime.py` and explicitly says not to edit it by hand. The router, declarative input algebra, generated traces, renderer, adapters and acceptance contracts must remain consistent.

Legacy components are not all horizontal. `vertical_scroll_selector:draw()` shows the selected choice plus its adjacent choices vertically. `control_scroll_selector` traverses an arbitrary set of controls; `list_selector` draws one label and one current value. The inconsistency is principally in the live presentation and control contracts, not evidence that every choice needs a newly written selector.

## Provisional control contract

Start by keeping the established encoder meanings and making their consequences visible. Avoid changing three controls at once merely to obtain visual consistency.

| Control | Consistent default | Required exceptions and safeguards |
|---|---|---|
| E1 | Open the current context's task list; within that task list, move between destinations | Today E1's task movement is one row per event, including a large encoder event. Held channel steps instead switch Masks/Trig Params, clamped. Preserve these initially, or approve and test a deliberate interaction change separately. |
| E2 | Move the selected row in an editable list, clamped at each end | Preserve stable field identity when returning. Pattern and output dashboards are not editable lists. Existing assignment selection is owned by its picker and must not acquire a second independent cursor. |
| E3 | Change the selected row's value; action rows show Open and read-only rows do not mutate | Preserve exact domains, sentinels and step sizes. Existing assignment owner uses E3 to browse choices. A consistent E2 list cursor there would require an intentional input migration, not only a layout change. |
| K1 short press | Open native PARAMS and return to the same Mosaic target/focus | Holding K1 remains the shift modifier. Do not turn a held modifier into a native-menu action or lose held grid keys. |
| K2 | Back or Cancel on destination/detail/draft screens, with visible contextual action | Masks currently use K1+K2 to clear channel step masks while preserving defaults; held-step K2 clears held steps. Trig Params K2 opens assignment; K1+K2 clears locks. Memory K2 undoes. A universal Back binding would break these functions. |
| K3 | Open a selected destination/action, or Apply a clearly marked draft | Masks are live edits, not unapplied drafts. Trig Params K3 toggles a slide; held-step K3 has the same musical role. Memory K3 redoes. Confirmations must commit exactly once. Show these actions explicitly rather than silently treating every K3 as Apply. |

The first implementation should make **selection consistent**, while retaining the documented distinction between live performance edits and staged settings. Requiring Apply after every held-step mask adjustment would alter musical workflow and memory recording. That is a separate product decision.

Suggested list display at 128 × 64: title/context at the top, an explicit scope line, four stable rows below, and a bottom action line. Selected row has a persistent arrow or inverse highlight. Labels remain on the left; exact values on the right. The viewport follows selection with neighboring rows visible, and a small position indicator distinguishes a long list from the entire menu. Long labels may use a deliberate short label; the selected field must have a route to its full label and exact value. Do not depend on scrolling text to reveal an essential value.

Always display Channel / Song slot / held-step scope. Multiple held steps need an explicit count or set summary and Mixed where their values disagree. Off, None, Inherit, zero and a cleared lock are distinct states. The existing runtime text contract already recognizes these distinctions; preserve them.

## What can remain playful

`lib/ui_splash.lua` already implements a logo-based startup animation independently of musical state. Its comments and implementation state that any input skips the splash without consuming that input. Keep it and retain that acceptance condition.

`lib/ui_motion.lua` separates decorative drawing from the renderer. It provides the native MOSAIC > UI motion switch, a four-tile title mark that responds to edits/apply, character poses, selection shadows, dial easing, focused-value rolling and text marquee. Animation does not consume `math.random` or emit MIDI/grid changes.

- Keep the startup logo, a brief highlight on the title mark, and small character blinks or beat gestures in space left after text is laid out.
- A selection may leave a faint settling shadow, but the real selected row and its values must appear immediately and remain fixed. Replace tile-grid glide with a list-compatible accent if useful.
- Remove movement of the essential value baseline (`vm.value_dy` in the focused renderer). Do not make the player wait for a rolling value to settle.
- Keep a dial or character only when it does not reduce label/value clarity. Large artwork belongs on status or dedicated musical-feedback screens, not squeezed between list rows.
- Marquee may remain for supplemental text. It should not be the sole way to identify a parameter or see its full current value. Motion-off mode needs the same meaningful information.

A uniform list does reduce the space for a large character on parameter-edit screens. That is an honest tradeoff. Mosaic can retain its personality in the startup, title feedback, dedicated musical views and small icons without retaining the one-field carousel layout.

## Risks that need acceptance evidence

1. **Scope ownership:** held steps must take precedence over feature Apply/Cancel; grid hold/release must restore the correct family and target. Two held steps, reversed release order, channel changes and grid disconnect must not edit an old target.
2. **Cursor ownership:** selecting a field by stable ID is safer than numeric index when Clock/Shuffle exposes different rows, a device changes its supported parameters, or the assignment list becomes sparse. Returning from a child, native PARAMS or MIDI-triggered temporary masks view must restore the intended focus.
3. **Commit semantics:** list navigation must not apply a draft. Cancel, repeated Apply, invalid Apply and leaving an editor must preserve the existing owner contracts. Device edits, scale confirmation, feature drafts and destructive confirmations are different operations.
4. **Clearing and sentinels:** preserve channel defaults while clearing step masks; distinguish X/unset from an explicit zero; do not clear another slot's lock or slide. Memory undo/redo must still restore the exact audible phrase and truncate only its own history.
5. **Performance and output:** scrolling through menus must send no unexpected MIDI or change grid LEDs/musical state. Decorative motion and longer row labels must not add musical recomputation or excessive redraw. Controlled time cannot prove physical-norns scheduling accuracy.
6. **Visibility:** long device names, negative/fractional values, chord intervals, ten trig slots, empty assignment lists, Mixed values and unavailable devices must remain understandable at native resolution with motion enabled and disabled.

## Tests and manual migration

The existing coverage is useful evidence to retain, not a complete oracle for the proposed design. Add a failing acceptance for the new list presentation on the current revision before production edits. Preserve source identity and the original failure artifacts. Do not weaken existing musical assertions to accommodate a changed screen.

Case families above are scope pointers. A case that verifies emitted music may not assert the new list's visibility; it must be complemented by a specific screen oracle. Conversely, a changed screenshot cannot replace an emitted-MIDI, persistence or scope oracle.

Relevant fast coverage lives in `lib/tests/lib/ui_router_tests.lua`, `ui_live_tests.lua`, `ui_render_footer_hints_tests.lua`, `ui_overview_cells_tests.lua`, `ui_motion_tests.lua`, `ui_marquee_tests.lua`, `ui_splash_tests.lua`, and the `ui_adapters_*_tests.lua` modules. The declarative model contract and generated router traces under `docs/ui-reimplementation/` need regeneration and checks when layout/input definitions change. Existing behavior navigation helpers (`tests/behaviour/ui.py`, `ui_map.py`) must use the public inputs for the new UI; do not change the emulator or use internal state as the sole acceptance oracle.

Proposed sequence:

1. Agree the list layout and the retained control exceptions, then write acceptance procedures for Masks, Trig Params and Clock. Include bounds, large encoder deltas, long labels, multi-step holds, native return and motion off.
2. Prove the new presentation assertions fail on the unmodified UI. Keep existing musical oracles unchanged.
3. Implement one shared list renderer and registry changes for these pilot screens. Keep owner adapters responsible for musical edits. Regenerate runtime spec and traces from their authoring source.
4. Extend the same pattern to Scale, Song, device/assignment, feature editors and Doctor setup. Keep musical diagrams and dashboards explicitly separate.
5. Run affected unit/integration coverage and applicable actual-app real-time and controlled-time behavior tests; preserve inapplicable-lane reasons. After implementation settles, run the full Lua suite and required campaign scope once. Shard reports remain incomplete until the aggregate inventory actually passes.
6. Capture new framebuffer/grid evidence under `images/`, regenerate scenes, and update README, quick reference and authoritative manual entries together. Every changed UI route needs new images and procedures. Historical tests and old source identities remain distinguishable from new captures.
7. Rewrite teaching scenes around a practical musical goal and coherent starting project. Behavior evidence validates the lesson but does not supply its narrative. For example, demonstrate adding a quieter offbeat to a working drum phrase, then hear the changed phrase; do not make a newcomer traverse a regression's failure boundaries as their first lesson.

The Astra review in `manual/ADVERSARIAL_REVIEW.md` identifies this last distinction: checkpoint evidence is valuable, but testing structure must not dictate teaching order. Realigning the instrument improves learnability; it does not by itself repair hidden chapters, disjointed contents or incompatible example starting states. Those editorial and navigation changes remain necessary.

## Assessment limits

This assessment inspected the actual fresh working tree on branch `manual/1.4.0-interactive`, including the live router/renderer, registry, legacy page owners, motion implementation and existing behavior catalog. It did not launch a native emulator, change production code or tests, run a new acceptance campaign, or establish physical-hardware performance. The control table is a proposal grounded in current behavior, not a claim that all menus already follow it.
